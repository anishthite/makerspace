Decisions

IDChoice · Rationale
D-001Wrap piSession.agent.streamFn and emit first_llm_call_start immediately before the provider stream call. This marks the actual LLM request boundary.
D-002Use client-side submittedAtMs and host receive time for the persisted metric. It covers browser/script submission and avoids trusting cross-VM clock sync.
D-003Prewarm the SDK session after bridge auth upload. It moves import/model/session setup off the post-submit path for ready bridges.
D-004Serve chat prompts from reusable warm bridges when available. Cold VM provisioning cannot meet a subsecond submit-to-first-call target.
D-005Use HTTP bridge auth upload instead of post-provision SSH seeding. Fresh SSH was flaky and inline auth exceeded exe.dev's setup-script size limit.

Tradeoffs

IDPicked over Rejected · Reason
T-001Conservative measured event over provider internals. The SDK does not expose a dedicated provider-call-start hook.
T-002Live benchmark script over unit-only timing. The goal is end-to-end latency through the app and exe.dev bridge.
T-003Warm reusable bridge over fresh VM per prompt. It is the only path measured below 1000 ms.

Assumptions

  • A-001 · A warm bridge may be reused for separate one-shot prompts. If wrong: set WARM_BRIDGE_POOL_SIZE=0 and accept cold-start latency.

Reversibility

R-001 · medium. Set WARM_BRIDGE_POOL_SIZE=0 and remove timing fields, metric events, SDK prewarm, and warm-claim logic to restore one fresh VM per prompt.

Definition of done

  • Measurement command records baseline 39346 ms and final latencies 239/553/392 ms.
  • Raw outputs are captured under implementation-notes/artifacts/.
  • Three consecutive measured runs report first_llm_call_start < 1000 ms.
  • npm test passes.
