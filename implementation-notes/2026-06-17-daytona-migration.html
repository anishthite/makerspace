Summary

Goal
Replace exe.dev SSH provisioning with Daytona SDK sandboxes while preserving threads, bridge runs, host dispatch, manual sessions, images, and settings.

src/provider.js, src/server.js, src/host-pi-runner.js, Genasite backend-daytona/src/agent/sandbox/daytona.ts as reference only.

Algorithm

  1. Instantiate Daytona lazily from env and keep SDK calls behind src/provider.js.
  2. Create or reuse a sandbox by name plus labels, apply lifecycle intervals, then run buildSetupScript() with env vars through process.executeCommand().
  3. Expose bridge URLs through getPreviewLink(port); pass x-daytona-preview-token for app-server requests while retaining the bridge bearer token.
  4. Replace host-dispatch SSH with Daytona process.executeCommand() and fs.downloadFile()/uploadFile().
  5. Poll manual-session output by executing the same log-envelope shell inside the sandbox instead of SSH.

Decisions

IDChoice · Rationale
D-001Use @daytona/sdk instead of @daytonaio/sdk. Daytona renamed the package and current docs use @daytona/sdk.
D-002Keep the existing provider method shape. This minimizes server/UI churn while changing the transport.
D-003Use Daytona preview tokens only from server-to-sandbox requests. Browser clients continue to talk to the makerspace backend, not directly to Daytona.
D-004Upload both Pi auth and Pi settings to bridge sandboxes. Auth alone produced no assistant output in live smoke.
D-005Return from /auth before bridge session warming completes. Long model/session initialization should not make auth upload look failed.

Tradeoffs

IDPicked over Rejected · Reason
T-001execute setup script after create over provider-native setup-script support. Daytona SDK exposes process execution and keeps bootstrap logic reusable.
T-002provider remote helpers over a new generic abstraction layer. One provider is required and the contract stays testable.
T-003omit resources for snapshot creates over forcing CPU/memory/disk on every create. Daytona rejects resources when using snapshots.

Assumptions

  • A-001 · Daytona sandboxes can run shell commands, serve preview ports, and upload/download files through SDK APIs. Verified by 2026-06-17-daytona-provider-smoke.txt.
  • A-002 · Daytona credentials are already available in env for smoke checks. Verified by live smoke artifacts without printing values.
  • A-003 · A Node-capable Daytona snapshot/image is available via DAYTONA_SNAPSHOT or default Daytona image. Verified by bridge health and run smoke.
