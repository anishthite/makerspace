API contract

GET /api/auth/openai-codex
→ { configured, source, expiresAt?, updatedAt? }

POST /api/auth/openai-codex/login
→ { id, status, device: { verificationUri, userCode, ... } }

GET /api/auth/openai-codex/login/:id
→ { id, status, device?, progress?, error? }

Algorithm

  1. Require the existing GitHub app user for hosted /api/auth/openai-codex* routes.
  2. Run Pi AuthStorage.login('openai-codex') in memory for hosted users.
  3. Encrypt the resulting OAuth credential under user-secret:openai-codex.
  4. When launching a user-owned bridge, write {"openai-codex": credential} to remote auth.json.
  5. For server-side title/summary calls, use an in-memory Pi auth storage seeded from the session owner’s credential.

Decisions

IDChoice · Rationale
D-001Keep GitHub as the Makerspace account id. OpenAI Codex auth identifies model entitlement, not app ownership.
D-002Use Pi’s OAuth login instead of copying Board’s direct OpenAI endpoint calls. This follows Pi’s current provider implementation.
D-003Store one encrypted JSON credential per user. The existing auth store already handles file/D1 persistence and encryption keys.

Tradeoffs

IDPicked over Rejected · Reason
T-001Bridge auth.json sync over env vars. Pi already refreshes OAuth from auth storage.
T-002No token-refresh back-sync from sandboxes. Board ships the same shortcut; users can re-login if refresh rotation invalidates stored tokens.
