Algorithm

  1. Chat launches mark the session as bridgeMode and reserve the shared proxy port for the bridge.
  2. Setup writes a tiny pi-bridge.mjs daemon, an env file, and a systemd unit; boot starts the bridge but not pi.
  3. After VM creation, the server waits for /healthz, then starts a run via POST /runs.
  4. The server follows the bridge SSE in the background and mirrors those events into an in-memory event log.
  5. The browser opens one SSE connection to the server; the server replays buffered launch events and then pushes live bridge events.

UI layout

  1. Chat transcript: append SSE chunks as they arrive; stop on done.
  2. Status banner: use launch/bridge/run status events instead of poll warnings.
  3. Session table: keep SSH/debug commands; chat sessions expose the bridge URL as the shared URL.

Decisions

IDChoice · Rationale
D-001Use a tiny VM-local bridge instead of SSH tailing. Keeps the remote protocol structured and removes repeated SSH command execution.
D-002Use SSE, not WebSocket, for browser delivery. One-way output is the only thing the current UI needs.
D-003Reserve the shared proxy port for the bridge on chat launches. Smallest path; app previews can come back when dual-port routing is actually needed.

Tradeoffs

IDPicked over Rejected · Reason
T-001systemd bridge daemon over ad-hoc nohup. Slightly more setup, cleaner restarts and logs.
T-002server-side bridge relay over direct browser-to-VM connection. Keeps one stable app API and hides bridge tokens from the frontend URL surface.

Assumptions

  • A-001 · exe.dev's shared proxy URL reaches the single configured shared port for the VM. If wrong: fall back to an SSH tunnel only for backend-to-bridge transport.
  • A-002 · Chat sessions do not need a simultaneous app preview URL in v1. If wrong: add dual-port routing or a second transport later.

Reversibility

R-001 · medium. Re-enable SSH polling and remove the bridge setup/service if the proxy path proves unreliable.

Definition of done

  • Chat runs start pi through a VM-local bridge, not by auto-running it directly in the setup shell.
  • The browser receives streamed output from one SSE connection to the app server.
  • SSH remains in the provisioning path only for chat runs.
  • Tests pass.
