Algorithm

  1. Base from node:22-bookworm-slim; install only git, curl, and certificates.
  2. Install image/package.json once into /home/daytona/.pi/agent/npm.
  3. Symlink /usr/local/bin/pi to /home/daytona/.pi/agent/npm/node_modules/.bin/pi.
  4. Set bridge setup to load SDK from /home/daytona/.pi/agent/npm instead of bridge-sdk.
  5. Create Daytona snapshot makerspace-pi-tiny-v2; point DAYTONA_SNAPSHOT at it after smoke passes.

Decisions

IDChoice · Rationale
D-001Use a Daytona snapshot instead of imageRef. Existing provider already selects DAYTONA_SNAPSHOT when settings keep imageRef="".
D-002Keep the image root-based. Current Daytona Node snapshots execute setup as root, and creating a daytona user would make missing sudo matter.
D-003Keep makerspace-pi-tiny over makerspace-pi-boardstyle. The Board-style base is larger and did not improve measured startup.
D-004Supersedes: D-001. Use makerspace-pi-tiny-v2 with one npm prefix. It removes the global plus bridge duplicate install.
D-005Use --legacy-peer-deps for runtime package install. pi-simplify advertises a stale peer range but already worked in the prior image.

Tradeoffs

IDPicked over Rejected · Reason
T-001node:22-bookworm-slim over Ubuntu/systemd. The bridge path needs Node, git, curl, Pi, and npm packages.
T-002Preinstall npm extensions over only preinstalling Pi. Local Pi settings otherwise reinstall those packages during Starting pi.
T-003node:22-bookworm-slim over cloudflare/sandbox:0.12.1. Cloudflare base adds about 264 MiB root filesystem and no recurring Daytona cost advantage.
T-004One npm prefix over separate global and bridge installs. Snapshot smoke drops root filesystem from 988M to 510M.

Assumptions

  • A-001 · Daytona accepts a plain long-running container entrypoint. If wrong: snapshot smoke fails before app config changes.
