Summary

Goal
Keep the VM bridge transport, but run Pi through the SDK instead of spawning pi -p.
Source
User wants the bridged architecture to use the SDK, not CLI stdout as the runtime interface.
Surface
src/setup-script.js, image/Dockerfile, README.md, public/index.html, test/setup-script.test.js.
Schema
None.
Runtime
Bridge keeps POST /runs and GET /runs/:id/stream; only the VM-side execution engine changes.
Open Qs
0.

API contract

VM bridge request
POST /runs
{ "id": string, "name": string, "prompt": string }

Bridge SSE payloads
{ "type": "stdout", "chunk": string, "runStatus": "running" }
{ "type": "status", "runStatus": "completed" | "failed", "done": true, "exitCode": number }

SDK event mapping
message_update.text_delta -> stdout chunk
tool_execution_update.partialResult -> stdout delta
tool_execution_end.isError -> [system] ... failed line

Algorithm

  1. Install or reuse @earendil-works/pi-coding-agent in /home/exedev/.pi/agent/bridge-sdk.
  2. Resolve that package from pi-bridge.mjs with createRequire(...).resolve(...).
  3. Create one in-memory Pi session with createAgentSession({ cwd, sessionManager: SessionManager.inMemory(...) }).
  4. Map SDK text and tool events into the existing bridge stdout/status SSE envelope.
  5. Leave the server and browser relay contract unchanged.

Decisions

IDChoice · Rationale
D-001Keep the bridge HTTP/SSE contract stable. Server and browser already speak that shape.
D-002Install the SDK into /home/exedev/.pi/agent/bridge-sdk. The standalone pi binary is not importable by Node.
D-003Use SessionManager.inMemory(...) in the bridge. One prompt maps to one VM-backed run; no extra session files needed.

Tradeoffs

IDPicked over Rejected · Reason
T-001SDK event mapping over spawn('pi', ['-p', ...]). Structured events beat terminal text scraping.
T-002local package import path over global npm resolution. Deterministic path works with both the baked image and setup-script fallback.

Assumptions

  • A-001 · pi --version matches an installable npm package version. If wrong: pin the bridge package separately.
  • A-002 · The current frontend still only needs the bridge's coarse stdout/status stream. If wrong: expose richer event types later.

Reversibility

R-001 · medium. Restore the old child-process bridge path and remove the local SDK package install if the SDK-backed bridge misbehaves on real VMs.

Definition of done

  • The generated bridge script imports Pi through the SDK.
  • The image bakes the same SDK package path the bridge expects.
  • Docs and tests mention the SDK-backed bridge.
  • npm test passes and the extracted bridge script parses with node --check.
