00

recommended shape

方針

one app, two providers

Local should use your computer. Cloud should use Daytona.

Do not fork the product. Keep one browser UI and one backend API, then swap only the infrastructure provider: local uses git worktrees and local bridge processes; daytona uses hosted sandboxes and preview URLs.

Provider flagtarget
INFRA_PROVIDER=local npm start
INFRA_PROVIDER=daytona npm start
01

the whole architecture

全体図 
Browser UI
  │
  ▼

  ▼
Provider adapter
  ├─ local   ── git worktree + localhost Pi bridge process

The invariant: the browser never cares where the work runs. It always talks to the backend.

02

provider split

二系統

local provider

Runs on this computer Creates a repo worktree, starts the same Pi bridge on 127.0.0.1, and streams through the backend. 
~/.makerspace/
  repos/<repo-hash>.git
  worktrees/<agent>/
  control/<agent>/
  logs/<agent>.log

daytona provider

Runs in hosted sandboxes Creates or reuses a Daytona sandbox, starts the sandbox-local Pi bridge, and reaches it through a preview URL. 
Daytona sandbox
  /srv/workspace
  /srv/makerspace
  preview :4310
  autostop/autodelete
03

local worktree flow

局所実行
  1. Backend receives POST /api/threads with repo, branch, agent name, and prompt.
  2. Local provider keeps a bare repo cache at ~/.makerspace/repos/<repo-hash>.git.
  3. It runs git fetch, then creates git worktree add ~/.makerspace/worktrees/<agent>.
  4. It creates ~/.makerspace/control/<agent> for status files, logs, bridge auth, and run state.
  5. It starts the bridge as a child process with PI_BRIDGE_WORKSPACE_DIR pointing at the worktree.
  6. Backend talks to http://127.0.0.1:<port>, then relays output to the browser over the existing SSE route.
04

same backend contract

不変部分
createSession()Local creates worktree + bridge. Daytona creates sandbox + bridge.
destroySession()Local kills process + removes worktree. Daytona deletes sandbox.
readOutput()Both read the same pi.log and STATUS envelope.
runRemoteScript()Local runs shell in worktree. Daytona runs shell in sandbox.
readRemoteFile()Local reads mapped files. Daytona downloads files through SDK.
bridgeHeaders()Local returns none. Daytona adds preview-token headers.
05

desktop app path

後工程
Phase 1: local daemon Ship INFRA_PROVIDER=local as a Node backend plus browser UI. Fastest path, smallest diff.
Phase 2: provider toggle Add a settings switch for local vs daytona; keep env override for deploys.
Phase 3: desktop shell Wrap the same backend/UI with Tauri or Electron for tray, autostart, file pickers, and bundled runtime.

Desktop should be packaging, not a second architecture.

06

what not to build yet

削除候補
No mock outputLocal mode should run real Pi so bugs are real.
No Docker firstWorktrees cover most dev bugs; add Docker only for Linux isolation or resource limits.
No separate local UIOne frontend keeps Daytona and local behavior honest.
No file sync layerLocal already has files; Daytona can stay repo-based until sync is required.
